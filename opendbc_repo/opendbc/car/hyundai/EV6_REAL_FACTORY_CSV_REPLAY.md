# 2022 EV6 순정 자동주차 CAN-FD 실제 로그 재생 검증 (읽기 전용)

## 테스트 조건

- 자료: 기존 사용자가 제공한 `extract_6.csv` (좌), `extract_7.csv` (우).
- 기록은 차량 CAN 데이터의 **기존 로그**다. 이 시험에서 차량/ECU에 통신을 연결하거나 새 명령을 송신하지 않았다.
- 원본 CSV 전체(약 1.17MB/1.15MB)는 PR에 포함하지 않았다.
- 비교 원작: `ajouatom/openpilot`의 `joongyu01/carrot-wip-dev`.
- 재생기: `ev6_spas_factory_replay.py` (오프라인, CAN/UDS/소켓 TX 없음).
- 기존 계획기: `ev6_spas_control.py`, 수신 전용 `passive_spas2_snapshot`.
- `bus=0`인 0x165 / 0x16A / 0x413만 OEM 관찰 근거로 사용;
  반환/복제된 2/128/130 소스는 독립 ECU 송신으로 계산하지 않음.
- SPAS1/2 길이·CRC16/XMODEM, 증가하는 카운터, 방향명령 onset 및
  실제 0x413 램프 OFF→ON 피드백을 검사한다.

0x165/0x16A counter가 1회씩 건너뛰었다.

## 원작 포팅에 주는 결론

1. `spas.py:frame()`의 대부분 바이트 0-fill SPAS2 프레임은
   실제 EV6 방향 명령 시작 프레임과 다르다. 특히 factory-on
   raw byte7=0x01, byte18=0x40이다.
2. 명령이 유지되는 동안 byte7/18 조합이 **8종 이상 변할 수 있으므로**
   `0x01/0x40`을 전체 지속시간 동안 하드코딩하는 것 역시 순정
   작동을 재현하지 못한다.
3. `hyundaicanfd.py:create_spas_messages()`의 OEM template
   복사는 더 많은 비트를 보존할 수 있지만, idle 상태의 템플릿을
   그대로 재사용해 방향명령만 덮어쓰는 것이 순정의 상태 전환과
   같다는 증거는 없다. 관련 바이트의 목적/인과는 여전히 미상.
4. 원작의 엄격한 `safety_hyundai_spas.h` TX 검사는 해당 byte7/18의
   비제로 factory-on payload를 그대로 승인하는 경로가 아니다.
   panda 예외를 열거나 우회해서 차량에 실험하는 조치로 해결하지 않는다.
5. 기존 0x7B1/0x7B9 진단 세션 시도는 **이 두 로그에 없다**.
   실제 ECU 인계 승인·순정 SPAS 송신 정지·복구를 입증하지 못한다.

기존 좌·우 CSV 파일을 `ev6_spas_state_timeline.py`로 한 번 더 재생했다.
새 분석기는 실제 bus0의 CRC-valid SPAS2만 이용해 방향 명령 시작과

**좌·우 두 기록에서 실제 관측한 상태 전환 순서는 동일하다.**

~~~text
(byte7 / byte18)
01/40 → 01/46 → 0D/46 → 1A/46 → 0D/46 →
0D/40 → 0D/45 → 0E/45 → 0E/40 → 0E/45
~~~

그러나 상대 시각은 다르다. 예를 들어 두 번째 조합 `01/46`이
나타난 시각은 좌측 명령 시작 후 5.4361초, 우측은 3.3574초이다.
따라서 이 패턴은 특정 시간에 맞춰 외부에서 보내면 된다는 의미가
아니다. 이들 바이트는 주차 동작의 여러 단계나 다른 시스템 상태의
표현일 수 있으며, 램프 점등에 대한 원인·필수조건은 검증되지 않았다.

검증: 기존 상태 계획기 39개 + 기존 factory CSV 재생기 10개 +
새 raw 상태 타임라인 시험 8개 = **57/57 Python unittest PASS**
(로컬 Python 3.13.5). `py_compile` 통과 및 세 수신 전용
Python 모듈에 대한 AST CAN 송신 API 부재 검사도 통과했다.
전체 GitHub Actions/실 ECU/실제 panda 안전 검증 완료를 의미하지 않는다.

새 테스트는 잘못된 버스·CRC·시간 역전·명령 시작/종료 누락과
좌·우 순서 같지만 시간 차이가 나는 사례를 검사한다. 본 분석기는
기존 로그로부터만 관찰 정보를 추출하며 실제 CAN/UDS 신호를 만들거나
전송하지 않는다.

## 관측 시각 보정: 실제 램프 지연값으로 해석하지 말 것 (2026-11-25)

위 표의 `29.4ms / 10.2ms`는 `0x413` 램프 상태의 **첫 ON 수신 표본**
시각과 SPAS2 제어값 변경 시각의 차이다. 이것이 실제 전구/LED가
점등된 물리적 시점이라는 의미는 아니다. 기존에 '실제 램프 ON까지
지연'으로 표현한 서술은 이 범위 안에서만 해석해야 한다.

좌측에서는 요청 후 +9.2ms OFF와 +29.4ms ON 사이(20.2ms 표본 구간)에
상태 변화가 기록됐다. 우측에서는 요청 **전** -71.9ms OFF와
요청 후 +10.2ms ON 사이(82.1ms 표본 구간)에 상태 변화가 기록됐으므로,
물리 램프가 제어 명령 이후에 켜졌다는 선후관계를 확정할 수 없다.

추가로 SPAS2 방향 제어값 3/4는 유지되는 동안에도 램프 ON/OFF 표본
전환이 좌측 68회, 우측 60회 기록됐다. 특히 raw byte7/18 조합이
8초 이상 동일한 구간에도 24회 이상 전환이 기록됐다. 이는 해당
raw 바이트의 모든 변화가 개별 램프 깜박임을 직접 구동한다는 가설과
일치하지 않는다. 모든 상태 바이트가 무관하다는 결론도 아니다.

**상세 재생 결과와 측정 한계:** `EV6_SPAS2_LAMP_CADENCE_OBSERVATIONS.md`.

- 원본 bus0, 8바이트, CRC8 poly 0x1D / init 0 / xorout 0x65
  (`data[1:]`)가 유효한 프레임만 인정

  양쪽 모두 존재하고, 그 구간에 관측된 레버 프레임 전부 중립일 때만
  `factory_event_neutral_lever_corroborated=True`
- 비중립 레버, CRC 오류, 다른 CAN 버스, 없는 전·후 표본, 오래된
  표본, 정확히 같은 시각의 **한 표본을 전·후 중복 계산하는 사례** 및
  bus0에 0x7B1/0x7B9이 함께 기록된 경우는 해당 근거를 거부

  SPAS2↔0x413 **기록상 시간 상관**만 뜻하며, 레버 중립 및
