# 2022 EV6: 순정 자동주차 방향지시등과 0x3C1 레버 신호의 분리

이 자료는 사용자가 제공한 **순정 자동차 rlog (6).zst, rlog (7).zst**의
실제 CAN 버스 0 수신 기록만을 비교한 **오프라인 분석** 결과입니다.
외부 장치의 SPAS2 송신·ECU 제어권 확보 가능성을 보여주지는 않습니다.

## 실측 비교 (버스 0, 순정 수신만)

| 항목 | 좌측 rlog(6) | 우측 rlog(7) |
| --- | ---: | ---: |
| 전체 순정 레버 0x3C1 프레임 | 309 | 306 |
| 방향 조작 비트 byte3/4 모두 0 | **309** | **306** |
| 0x3C1 CRC8 오류 | 0 | 0 |
| 순정 램프 0x413 실제 ON 피드백 | 148 | 126 |
| SPAS2 0x16A 방향 명령 프레임 | 3번: 1,197 | 4번: 1,043 |
| 최초 SPAS2 명령 전환 시각 | 16.8990 s | 20.3122 s |
| 최초 램프 ON 관측까지 지연 | 약 29.4 ms | 약 10.2 ms |

레버 CRC8: poly=0x1D, init=0, xorout=0x65, bytes[1:8].
레버 조작 상태: bytes 3/4. 램프 ON: 0x413 byte2 bit 4(좌), bit 6(우).

**관측 사실:** 순정 자동주차로 방향지시등이 실제 켜질 때
0x3C1 스톡 레버 입력은 처음부터 끝까지 중립이었습니다.
따라서 **순정 자동주차는 0x3C1 레버 조작을 필요로 하지 않는
별도의 점등 경로를 사용한다는 강한 증거**입니다. SPAS2 명령
전환과 램프 점등 간 시간 상관이 직접 관측됐습니다.

## 추가 검증: SPAS2는 방향 명령만으로 구성되지 않는다

원본 rlog(6), rlog(7)의 순정 버스 0 수신 데이터를 상태별로 비교:

| 관찰 항목 | 좌측 자동주차 | 우측 자동주차 |
| --- | --- | --- |
| 최초 방향 명령 | 16.899초, `BLINKER_CONTROL=3` | 20.312초, `BLINKER_CONTROL=4` |
| SPAS2 바이트 3 | 활성 구간에서 0x26 | 활성 구간에서 0x26 |
| SPAS2 바이트 18 | 초기 0x00 → 명령과 함께 0x40; 이후 0x45/0x46도 관측 | 20.291초에 0x00→0x40, **약 21ms 후** 방향 명령 4 |
| 순정 SPAS1 바이트 3 | 0x4b | 0x48/0x49/0x4b 등 상태 변화 관측 |
| 방향 명령 해제 | 40.838초에 명령 0 | 41.171초에 명령 0 |

상태 바이트 3/18은 아직 **공식 신호 의미가 확인되지 않은 원본 오프셋**
이다. 이 숫자는 외부 송신용 템플릿이나 제어 메시지를 구성하라는
뜻이 아니다. 순정 주차 ECU가 방향 비트와 함께 여러 상태를 송신한다는
관찰이며, `BLINKER_CONTROL=3/4`만 바꾸는 기존 실험 코드의
기능적 완성도가 입증되지 않았음을 보여준다.

## 추가 검증: CAN 기록의 서로 다른 src를 ECU 개수로 착각하지 않기

별도로 추출한 rlog(6)/(7)의 SPAS1/2 수신 기록을 비교했다.

| 구분 | 좌측 rlog(6) | 우측 rlog(7) |
| --- | ---: | ---: |
| SPAS2 `src=0` | 3,104 | 3,066 |
| SPAS2 `src=2` | 250 (약 4.963초까지) | 222 (약 4.414초까지) |
| SPAS2 `src=130` | 2,855 (약 4.963초부터) | 2,844 (약 4.455초부터) |
| `src=2` 프레임이 `src=0`의 시각+페이로드와 정확히 일치 | 248건 | 222건 |
| `src=130`이 `src=0`의 시각+페이로드와 정확히 일치 | 2,831건 | 2,823건 |

`src=130`은 panda 기록에서 전달/반환된 버스 2 프레임을
구분하는 값이며, **두 번째 주차 ECU가 독립적으로 보냈다는 근거가
아니다**. 실제 좌/우 방향 명령이 시작되는 16.899/20.312초에는
`src=2` 직접 수신 방향 명령이 없고 `src=0`과 전달 기록이 관측된다.
이 정보만으로는 ECU의 물리 배선, 게이트웨이, 소유권을 확정할 수
없으므로 실차에 같은 ID를 추가 주입할 정당화 근거로 사용할 수 없다.

원본 rlog는 읽기 전용 Cap'n Proto 분석기로 재검증했다. 좌측
0x3C1 309개, 우측 306개가 전부 CRC8 정상이며 조작 비트 중립이고
각각 램프 ON 148/126개가 확인됐다. 별도의 8개 단위 테스트는
로컬에서 동등한 분석 함수를 분리 실행해 통과했다. 전체
openpilot/LogReader 환경의 통합 실행은 아직 검증되지 않았다.

## 지금의 두 경로 평가

| 제어 경로 | 증거 | 해결되지 않은 점 |
| --- | --- | --- |
| 0x3C1 레버 사칭 | rlog(8): 호스트 3회 전송했으나 외부 램프 점등 없음 | BCM 수락 여부와 점등 선행 조건 미확인; 여러 프레임 재송신은 같은 ID 충돌 위험 |
| SPAS2 0x16A | rlog(6/7): 순정 주차 ECU가 3/4를 발신하며 실제 램프가 점멸 | 외부 장치가 ECU 제어권을 얻거나 기존 송신과 충돌 없이 발신할 수 있는지 미확인 |
| 단순 플래그 ON | ms-xy-radar3에는 SPAS2 생성 함수가 존재하나 플래그가 꺼져 있음 | panda TX 허용 목록에 0x165/0x16A가 없고, ECU 비활성화의 부작용이 알려져 있음 |

따라서 **현재 우선순위는 SPAS2의 순정 동작을 수동적으로 기록하고
실제 ECU 연결 방식과 충돌 방지 가능성을 별도 벤치에서 입증하는 것**입니다.
성공이 검증되지 않은 0x3C1을 무리하게 다회 재송신하거나 같은 ID를
계속 송신하는 시험은 권하지 않습니다.

원작 `ajouatom/openpilot`의 `spas.py`, `carcontroller.py`에도
순정 0x3C1과 충돌하는 송신으로 CAN bus-off가 일어난 기록과
일부 차량의 0x7B1 응답 부재가 명시돼 있습니다. 이는 사용자 EV6에서
같은 결과가 발생했다는 뜻은 아니지만 **차량에서 위험을 감수하고
수신 확인 없이 송신을 시작해서는 안 되는 근거**입니다.

### 버스 기록 재검증 명령

PR #43에 추가된 `ev6_spas_bus_route_audit.py`는 추출된 CAN CSV의
`t_sec,can_id,bus,payload_hex` 필드를 읽어 위 표의 source별
메시지 수, 시간 범위와 정확히 일치하는 프레임 수를 계산한다.

```bash
python tools/signal_analysis/ev6_spas_bus_route_audit.py extract_6.csv extract_7.csv --output ev6_spas_route_report.json
```

이 스크립트도 **read-only**이며 Panda, SocketCAN, UDS 송신 인터페이스를
사용하지 않는다. `src=130`의 물리적 송신 출처를 증명한다고
주장해서는 안 된다.

## 검증 자동화

`ev6_spas_oem_transition_test.py`가 이제 `factory_lamp_without_stalk`를
함께 출력합니다. 이는 순정 수신 0x3C1의 전수 CRC, 중립 상태,
실제 램프 ON 프레임 수를 자동으로 판정합니다.
`test_ev6_spas_oem_stalk_independence.py`는 이 분류기의 정상·누락·
오류 CRC·실제 레버 조작 사례를 확인하는 8개 소프트웨어 테스트입니다.

- 코드 자체는 **CAN을 송신하지 않습니다**.
- 추후 다른 차량의 레버 기록이 누락되거나 CRC가 틀리면
  `factory_lamp_with_all_observed_stalk_frames_neutral=false`로 처리합니다.
- 이 값이 true여도 '순정 자동주차 원리'에 한정됩니다.
  **사용자 명령으로 SPAS2를 송신해도 안전하다는 뜻이 아닙니다.**

실제 차량 제어 시험은 현재 **NO-GO**입니다.
