# EV6 0x3C1 실제 레버 / 호스트 시험 전달경로 비교 (2026-11-25)

**범위:** 이미 수집된 차량 CAN 로그 `rlog (3).zst` (순정 레버), `rlog (8).zst` (오픈파일럿 1회 시험)를 **오프라인으로만** 비교. 이번 분석에서 실제 차량에 명령을 보내지 않았으며 기존 주행 기능도 변경하지 않음.

## 1. 비교에서 확인된 원본 증거

| 항목 | 순정 운전자 레버 (rlog 3) | 실험적 오픈파일럿 송신 (rlog 8) |
|---|---|---|
| 방향지시등 명령 | 좌측 3프레임 (39.31/39.88ms 간격), 우측 3프레임 (40.96/40.53ms) | 좌측 1프레임씩 3번의 독립 시험 |
| `0x3C1` 예시 | 좌측 `3530304010000000`, 우측 `3750300041000000` | `8c20304010000000` |
| `0x3C1` CRC8 | 정상 | 정상 (3회 전부) |
| 버스 0 수신 `src0` | 실제 레버 3프레임 | 기존 순정 중립 메시지만 확인 |
| 버스 2 전달 에코 `src130` | 각 방향 명령 3회 매칭 | 호스트 시험 명령과 동일한 페이로드 0회 |
| 버스 0 호스트 TX 에코 `src128` | 해당 없음 | 시험 명령 3회 확인 |
| 실제 램프 상태 `0x413` | 순정 첫 좌측 명령 +9.19ms에 ON; 우측 +23.67ms에 ON | 총 304개 `0x413` 수신 프레임의 내용 동일, 변화 없음 |

마지막 시험에서 오픈파일럿 명령 송신 후 다음 *순정 중립 0x3C1*까지 약 **129.65ms** 떨어져 있었지만 외부 램프 상태는 바뀌지 않았다. 앞선 두 시험에서 다음 순정 프레임까지의 시간은 4.32ms / 7.90ms였다.

## 2. 확인된 CAN 경로 차이

기본 `ms-xy-radar3`의 `opendbc_repo/opendbc/safety/safety/safety_hyundai_canfd.h`에는 `hyundai_canfd_fwd_hook`가 존재한다. 이 함수는 버스 0에서 수신한 프레임을 버스 2로 전달(반대 방향도 가능)하며, `0x3C1`은 설정된 특수 buffering/forward-block 대상에 포함되지 않는다.

- 순정 운전자 레버: `src0`에서 방향 명령을 수신하며 대응되는 `src130`(버스 2 TX/전달 에코)도 관측.
- 호스트 시험: `sendcan bus0` 전송, `src128`(버스 0 TX 에코) 관측, **일치하는 `src130` 없음**. 이는 기존 수신 기반 전달 경로를 밟았다고 확인할 수 없다는 뜻.
- **주의:** `src128`은 차량 ECU의 수락 응답이 아니다. `src130` 부재만으로 외부 물리적 수신 ECU가 무조건 명령을 거부했다거나 그 ECU가 버스 2에 있다고 결론내릴 수 없다.

## 3. 원인 가설 우선순위

1. **전달경로/메시지 출처 차이 (우선 확인):** 순정 버스 0 RX -> 버스 2 전달과 오픈파일럿 버스 0 TX는 동일한 경로가 아닐 수 있다. 실제 방향지시등 제어를 수행하는 ECU가 어느 물리적 세그먼트에서 메시지를 받는지는 별도 확인이 필요.
2. **ECU의 명령 수락 조건 미확인:** 카운터·체크섬이 정상이어도 ECU의 자체 상태, 특정 연속 메시지, 네트워크 출처 또는 기타 인증/상태 조건을 만족하지 않을 수 있다.
3. **1프레임 부족 가능성:** 순정 레버는 3프레임이었지만 **첫 순정 프레임 이후 9.19/23.67ms에 램프가 켜졌고 두 번째 레버 프레임까지 약 39~41ms**가 걸렸다. 따라서 '무조건 3회 보내야만 점등한다'는 주장은 순정 실측 시퀀스와 맞지 않음.
4. **순정 프레임에 빠르게 덮여쓰임:** 첫 두 시험에서는 수 ms 후 중립 프레임이 관측됐지만, 세 번째 시험은 129.65ms 간격에도 실패했으므로 타이밍 하나만으로 설명하기 어렵다.

## 4. 다음 단계 / 중단 기준

- **안전한 현재 단계:** 실제 버스 물리 연결도, ECU 위치, 게이트웨이 장치와 전달 방향을 차량 제작사 자료와 격리된 버스 관측으로 확인. 기존 0x413/0x3C1 수신 분석 이외에는 명령 송신을 추가하지 않음.
- **실차 송신 금지:** 이 결과만으로 호스트에서 버스 2로 0x3C1을 추가 전송하거나 0x3C1을 여러 번 반복하는 코드를 배포하지 않음. 안전 정책 수정과 직접 송신은 독립 리뷰/하드웨어 검증이 필요.
- **SPAS2 경로와 분리:** 0x3C1 전달경로 문제와 0x16A SPAS2 ECU 제어권 문제는 별개의 시험. SPAS2는 원래 주차 ECU가 약 50Hz 송신 중이며 0x7B1 진단 통신 차단에는 기존 EV6 주차 기능 상실 보고가 있음.
- **가치 판단:** 이 로그로는 소프트웨어만 추가 수정해 곧바로 실제 점등이 가능하다고 보장할 수 없다. **현재 가장 구체적인 새 단서는 순정 레버의 RX→버스2 전달 에코와 호스트 TX→버스0 에코의 차이**이다.

관련 코드: `safety_hyundai_canfd.h`의 `hyundai_canfd_fwd_hook()`, `hyundai_canfd_tx_hook()`; `carcontroller.py`의 `_ev6_blinker_stalk_trial()`.

**상태:** 연구·시험 준비 문서. 차량 점등 기능 추가 아님. EV6의 외부 깜빡이 작동 여부 여전히 미검증.
